# Edit-Coverage Report — view-editability over the vendored parity corpus

Generated by `tests/parity-corpus/edit-coverage.spec.ts`. 57 tunes.

> **What "editable" means:** a unit is *structurally editable* when its note
> string round-trips into a StepGrid/PianoRoll model **that holds more than one
> thing** (the app's own `useGridModel` gate, plus invariant 3's third term —
> #1256), **or** it is an `arrange`/`pickRestart` clip control, **or** it is a
> master `all(x => …)` line the mixer's master strip edits.
> `note-broken` = the app would OFFER a grid/roll editor but the string does
> not round-trip (the "offered but blank" class). `knobs`-only = numeric
> params but no note/clip structure. Setup/boilerplate heads excluded, and so
> are units whose whole content is a single sound or a single note.

not units we are failing to serve — the mixer strip and the code line are their
editor, which is the same argument #998 used for host plumbing. Reported as its

## Blocker histogram — `note-broken` (offered a grid/roll but no round-trip)

> Bucketed by the **gate that actually stopped the write-back**, not by the
> first writer to decline (#990). Three writers stack behind one parse call
> — syntactic core → element projection → leaf projection — and the reason
> string used to be whichever spoke first, which is how "nested groups" led
> this list while not one of those units was stopped by nesting.
>
> `wrong-surface` = the values played belong to the other view. Under this
> harness's head routing (`note`/`n` → roll, `s`/`sound` → grid, as the app
> does) that is still an editability failure: the head asks for a view its
> own values cannot fill. It is only a non-failure in a sweep that asks BOTH
> surfaces of every unit — there, a drum pattern *should* decline the roll.
